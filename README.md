# Homelab Project - GitOps-Managed Kubernetes Cluster

A bare-metal Kubernetes cluster where **every change is a Git commit**. No `kubectl apply`, no
manual drift, no undocumented state. Flux CD reconciles the cluster against this repository
continuously; if what is running does not match what is committed, the cluster is wrong and gets
corrected automatically.

## Repository layout

```
clusters/staging/          # Cluster entrypoint — the only path Flux is bootstrapped against
├── flux-system/           #   Flux's own components (generated by `flux bootstrap`)
├── apps.yaml              #   Flux Kustomization → ./apps/staging
├── infrastructure.yaml    #   Flux Kustomization → ./infrastructure/controllers/staging
└── monitoring.yaml        #   Flux Kustomizations → ./monitoring/{controllers,configs}/staging

apps/
├── base/                  # Environment-agnostic manifests (Deployment, Service, PVC, Namespace)
└── staging/               # Overlay: composes base + adds tunnel config and encrypted secrets

infrastructure/controllers/  # Cluster-wide tooling (Renovate)
monitoring/
├── controllers/           # The kube-prometheus-stack HelmRelease itself
└── configs/               # Its configuration and encrypted secrets

.sops.yaml                 # Encryption policy: age recipient + which YAML keys to encrypt
renovate.json              # Tells Renovate to scan Kubernetes manifests
```

**The Importance of the split:**
They are separate Flux Kustomizations so the two can be reconciled — and rolled back — independently, and so
a broken config never blocks the operator itself from installing.

## How Reconciliation Works

1. `flux bootstrap` installed Flux into the cluster and pointed a `GitRepository` at this repo
   (`master` branch, SSH deploy key) with a root `Kustomization` watching `./clusters/staging`.
2. That root Kustomization applies `apps.yaml`, `infrastructure.yaml`, and `monitoring.yaml` — each
   of which is itself a Flux `Kustomization` pointing at a different subtree.
3. Every subtree is reconciled on a 1-minute interval with `prune: true`, so deleting a manifest
   from Git deletes the resource from the cluster. Git is the only source of truth.
4. Kustomizations containing secrets declare `decryption.provider: sops`, referencing the
   `sops-age` secret in `flux-system` that holds the age private key.

The tree is intentionally shallow — one root, four children. Debugging starts at
`flux get kustomizations` and reads downward.

## Stack and Reasoning

| Layer | Choice | Reasoning |
|---|---|---|
| Kubernetes | **k3s** | Single-binary install on a normal Linux host, so the OS stays inspectable — I can still `journalctl` my way out of a problem. Bundles Traefik and `local-path` storage. Helm controller disabled at install, since Flux owns Helm. |
| GitOps | **Flux CD** | Pull-based: the cluster reaches out, so no external CI system needs cluster credentials. Native Kustomize, Helm, and SOPS support with no glue code. |
| Templating | **Kustomize** | Patch-based overlays, no template language. Base manifests stay valid Kubernetes YAML that `kubectl` can read on its own. |
| Secrets | **SOPS + age** | Encrypts only the `data`/`stringData` values, so diffs on a secret's *structure* stay reviewable. age over GPG for a keypair that is one line, not a keyring. |
| Ingress (public) | **Cloudflare Tunnel** | Outbound-only. Nothing to forward, nothing to firewall, and my residential IP is never published. |
| Ingress (internal) | **Traefik** | Already in k3s; no reason to run a second ingress controller. |
| Observability | **kube-prometheus-stack** | One Helm chart for Prometheus, Grafana, Alertmanager, node-exporter, and the CRDs. Deployed with Flux `driftDetection` enabled, so manual Grafana tweaks get reverted. |
| Updates | **Renovate** | Runs in-cluster as an hourly CronJob and opens PRs against this repo — dependency bumps arrive as reviewable commits, which keeps the GitOps loop honest. |

## Secrets in a Public Repository

Every `Secret` here is committed **encrypted**, and it is safe:

```yaml
# .sops.yaml
creation_rules:
  - path-regex: .*.yaml
    encrypted_regex: ^(data|stringData)$
    age: age1ly7h0v...   # public recipient — the private key never leaves the cluster
```

- `encrypted_regex` limits encryption to secret *values*. Metadata stays plaintext, so a reviewer
  can see that a secret's name or namespace changed without being able to read what it holds.
- The age recipient in `.sops.yaml` is a **public** key. The matching private key exists in exactly
  two places: my workstation and the `sops-age` Secret in the cluster's `flux-system` namespace.
- Flux decrypts at apply time, in-cluster. Plaintext never touches Git or a CI runner.

Adding a new secret:

```bash
kubectl create secret generic my-secret \
  --from-literal=KEY=value \
  --dry-run=client -o yaml > my-secret.yaml

sops --encrypt --in-place my-secret.yaml
git add my-secret.yaml   # safe to commit
```
